Multi-Agent Deliberation & Debate Failure Modes

Research-triage sessions repeatedly surfaced papers analyzing why multi-agent LLM review/debate systems break down, including one paper on a structured 'critic' role for agentic code review.

  • "False consensus" is a named failure mode: agents converge on agreement without sufficient supporting evidence.
  • A single strategically adversarial or sycophantic agent can swing group accuracy substantially (reported 10-40% degradation, 30%+ more consensus on wrong answers).
  • Structured disagreement — a dedicated reviewer/critic role that must justify pushback — outperforms unstructured, unguided consensus-seeking.
  • Interaction structure (who talks to whom, and how disagreement is resolved) matters more for review quality than simply adding more agents.
Further reading
  • Adversarial Review: Structured Disagreement for Grounded Agentic Code Review (arXiv 2608.18167)
  • Talk Isn't Always Cheap: Understanding Failure Modes in Multi-Agent Debate
  • When collaboration fails: persuasion-driven adversarial influence in multi-agent LLM debate — Scientific Reports

LLM-as-Judge & Evaluator Design

Several triaged papers this week concerned how to design verifiers/judges that score agent or model outputs, including one finding that verifier-selection can beat near-perfect self-selection.

  • The strongest model isn't always the best judge — cost, latency, and self-preference bias (favoring outputs resembling its own family) all factor in.
  • Known systematic biases to guard against: position bias (favors placement), verbosity bias (favors longer answers), and self-preference bias.
  • Verifier/judge design hinges on four questions: how to construct the judge, how to prompt/aggregate it, how to evaluate the judge itself, and how to control its biases in deployment.
  • Validate a judge against a labeled holdout set and track agreement over time rather than trusting it out of the box.
Further reading
  • LLM-as-a-Judge in 2026: Top evaluation techniques and best practices — DeepEval
  • How to build LLM-as-a-Judge evaluators that hold up in production — Arize AI
  • LLM-as-a-Judge — Langfuse docs

Global Workspace Theory as a Lens for Agent Architectures

The research-triage committee runs a dedicated 'GWT voice' that repeatedly applied Global Workspace Theory to judge whether new agent papers had a genuine broadcast/coordination mechanism.

  • GWT models cognition as many specialist modules competing for access to a capacity-limited 'global workspace'; the winner gets broadcast to everything else.
  • The bottleneck is the point — a single shared channel is what lets otherwise-siloed modules coordinate at all.
  • Recent LLM cognitive-architecture papers (e.g. 'Theater of Mind') build literal GWT-style broadcast hubs on top of LLM agents, distinct from ad hoc multi-agent message-passing.
  • GWT gives a useful diagnostic: does a proposed multi-agent system actually have a workspace/broadcast construct, or just parallel isolated agents (its 'antithesis')?
Further reading
  • "Theater of Mind" for LLMs: A Cognitive Architecture Based on Global Workspace Theory
  • Global Workspace Theory — EmergentMind
  • CTM-AI: A Blueprint for General AI Inspired by a Model of Consciousness

Agent Skill/Tool Routing & Selection

Multiple triaged papers targeted the bottleneck of choosing which skill or tool an agent should invoke, rather than the agent's raw capability.

  • Routing quality, not agent capability, is often the real bottleneck — a better router can beat a better agent.
  • Skill-selection failures can starve good skills of usage even when they're available and correct (a 'credit starvation' pattern).
  • Self-evolving skill libraries can backfire past a critical pool size: a defective skill entering the decision context becomes reference material for later skills, forming contamination chains.
Further reading
  • SkillRouter — skill retrieval at scale for LLM agent ecosystems (arXiv 2603.22455)
  • When Self-Evolution Backfires: Pre-Commit Gating against Skill Contamination in LLM Agents (arXiv 2608.05810)

macOS launchd/Daemon Recovery After a Crash

A system crash prompted a root-cause check and recovery pass over launchd-managed daemons on the operator's machine.

  • launchd throttles restarts with a crash-loop guard (roughly a 10-second minimum period) to stop runaway respawning.
  • KeepAlive with SuccessfulExit set to false restarts a job specifically after it exits abnormally — that's the crash-recovery lever, not just Keepalive alone.
  • Editing a job's .plist doesn't take effect until you unload and reload it — toggling start/stop or enable/disable isn't enough.
  • Querying the state of a system-level Launch Daemon (vs. a per-user LaunchAgent) requires root.
Further reading
  • A launchd Tutorial
  • macOS launchctl commands — rakhesh.com

Tailscale SSH

The operator needed to reach a remote machine on the tailnet over SSH.

  • Tailscale SSH takes over port 22 for connections originating from the tailnet, authenticating and encrypting over WireGuard using Tailscale node identity — no separate SSH key management.
  • Enable it with `tailscale up --ssh` on first connect, or `sudo tailscale set --ssh` on an already-connected machine.
  • Access is governed entirely by the tailnet's ACL policy — without explicit rules, nobody can SSH in.
  • It doesn't touch sshd_config or authorized_keys, so existing non-Tailscale SSH access keeps working in parallel.
Further reading
  • Tailscale SSH — Tailscale Docs
  • Setting up a server on your Tailscale network — Tailscale Docs
