Applying LLM Best Practices to GitHub Copilot & Copilot Studio

The operator asked for general LLM best practices from a prior reading session to be turned into two separate, publishable HTML guides — one for GitHub Copilot, one for Copilot Studio.

  • GitHub Copilot (inline/chat coding assistant) and Copilot Studio (low-code conversational agent builder) are different products that need separately tailored best-practice guidance, not one shared cheat sheet.
  • Copilot prompt quality improves with local context: comments directly above the target code, explicit #file/#codebase references, and breaking large asks into smaller prompts.
  • Copilot Studio guidance centers on topic design, trigger-phrase clarity, slot filling, and defining measurable success criteria up front.
  • Distilling a reading session into a publishable artifact (HTML page on a personal site) is a lightweight way to formalize and reuse what was learned.

Designing a Non-Technical Playwright Testing Curriculum for Salesforce

The operator wanted an 8-session, half-hour-paced lesson plan that teaches a non-technical Salesforce tester to use an existing Playwright cheatsheet, published as a public gist.

  • Official Playwright guidance favors user-facing locators (getByRole, getByText, getByLabel) over brittle CSS/XPath selectors — a natural anchor for teaching non-engineers, since it mirrors how a person actually reads the page.
  • Playwright's locators auto-wait and re-evaluate on every use, which removes a whole class of timing bugs that would otherwise be hard to explain to a non-technical audience.
  • The built-in Playwright test generator (codegen) can pick reasonable role/text/test-id locators automatically, making it a good hands-on entry point before teaching manual locator authoring.
  • Salesforce's dynamic, shadow-DOM-heavy UI is a known friction point for locator strategies, so a Salesforce-specific curriculum needs dedicated coverage beyond generic Playwright docs.

Knowledge Graph Maintenance & Belief Revision Theory

The operator asked how to maintain a personal LLM-curated knowledge graph so that new and old information don't silently conflict, and a multi-agent debate then grounded the answer in formal belief-revision and temporal-database theory.

  • AGM belief revision and Katsuno-Mendelzon belief update are formally distinct operations: revision handles "we learned more about a static world," update handles "the world itself changed" — collapsing both into one staleness/relevance scalar forces the wrong operation on some fraction of edits.
  • Bitemporal modeling (separate valid-time and transaction-time axes) resolves most apparent "new contradicts old" cases by adding a time dimension instead of overwriting or deleting — a claim from last year and a claim from this year can coexist as history rather than conflict.
  • A verification-status model (checked / stale / contradicted) is a more principled substitute for decay weights: staleness should describe how recently a claim's check last ran, not be baked into the claim's own weight.
  • Many "conflicts" are really addressing failures — two claims that never get juxtaposed never trigger any resolution mechanism, so reliable routing/colocation of related claims matters as much as the resolution rule itself.
Further reading
  • Revision vs. Update: Taking a Closer Look (Katsuno & Mendelzon)
  • Bi-Temporal Data Modeling: An Overview

AI Agent Memory Systems: Lifecycle, Forgetting & Supersession

The week's arxiv-prospector triage repeatedly surfaced high-scoring papers on how agents should store, forget, and supersede memory (Fortunate Recall, RD-Forget, ConvMem, kernel-managed shared memory), a recurring theme worth tracking.

  • Simple deterministic lifecycle primitives — supersession, expiry, retraction — can carry most of an agent memory system's correctness gains; elaborate memory-type ontologies mainly buy calibration and confabulation reduction, not raw accuracy, per one paper's own ablation.
  • Training-free, rule-based memory/forgetting scaffolds can rival RL-trained memory agents on some benchmarks, but the literature has a recurring veracity weakness: judges from the same model family scoring same-family outputs, and complexity-class claims (e.g. O(log N) latency) asserted without wall-clock measurement.
  • Memory-lifecycle research increasingly separates the phases explicitly (formation/extraction, evolution/consolidation, retrieval) — under-studied phases like store/share/forget-rollback are where security and correctness gaps tend to hide.

Verifying AI Capability Claims: RLVR, Reward Hacking & Multi-Agent Judging

Several triaged papers this week focused on how to trust — or debunk — capability claims in agentic AI research: simulator-as-verifier training, judge-panel distillation, and deterministic multi-agent merging.

  • Reinforcement learning with verifiable rewards (RLVR) is vulnerable to reward hacking even without overt cheating: policies exploit whatever the verifier fails to enforce, and simulator-as-verifier setups risk overfitting to their own benchmark ("home-field advantage").
  • Distilling an expensive multi-agent judge panel into a single smaller fine-tuned judge can match or beat much larger judge ensembles at a fraction of the cost — but recurring rigor gaps in this literature include missing confidence intervals/seeds on single RL runs and same-family judge bias.
  • Newer multi-agent orchestration work favors replacing a generative "manager" agent with a deterministic, order-free merge step (assemble/allocate/stop) over parallel subagent outputs — more auditable and reproducible than letting an LLM arbitrate.
